## 一、背景与问题（为什么做）

- **现状**：系统目前是单用户模式，任何人打开页面都能看到全部数据，没有身份概念。
- **问题**：客户要求多用户数据隔离，销售把这条写进了合同，不做就没法交付。
- **不解决的后果**：合同违约，且后续所有涉及「谁能看什么」的需求都无从下手。

## 二、目标 / 不做什么

### deliverables（交付物）

- [x] 账号密码登录接口（POST /api/auth/login）
- [x] Token 校验中间件，挂在所有受保护路由前
- [x] 前端登录页 + 登录状态保持
- [x] 单元测试与接口测试

### out-of-scope（不做什么）

> ★ 这一节比 deliverables 更重要。需求膨胀全都发生在「顺手多做一点」上。

- ❌ 不做第三方登录（微信 / OAuth / 企业 SSO）—— 客户没提，接口形式完全不同
- ❌ 不做手机验证码登录 —— 需要短信服务商，成本和排期都不在本次范围
- ❌ 不做密码找回 —— 拆成独立需求 SPEC-004，本次只交付登录

## 三、需求描述

- **用户故事**：作为已注册用户，我希望用账号密码登录，以便只访问属于我自己的数据。
- **主流程**：
  1. 用户在登录页输入账号与密码
  2. 后端校验，成功则签发 token 并返回
  3. 前端保存 token，后续请求自动带上
  4. 后端中间件校验 token，通过则放行
- **边界与异常**：
  - 密码错误：返回 401，**提示语不区分「账号不存在」和「密码错误」**（防账号枚举）
  - 连续 5 次失败：账号锁定 15 分钟
  - token 有效期 2 小时，过期返回 401 并提示重新登录
  - 并发登录：允许，不做单点登录

## 四、技术方案与风险

- **方案概要**：JWT 签名 token，无状态校验，详见 `ADR-001`；实现细节复用 `modules/auth-jwt`
- **影响的模块 / 文件**：`api/auth/*`、`middleware/auth.py`、`web/login.*`、数据库 `users` 表新增 `failed_count` / `locked_until` 两列
- **风险点**：JWT 无法主动吊销，账号被锁后已签发的 token 在有效期内仍然可用（已接受这个代价，见 ADR-001 后果章节）
- **回滚方式**：中间件读取配置开关 `auth.mode`，改回 `session` 即回滚；数据库新增列可空，不影响旧逻辑

## 五、验收标准（validation）

> 每条都必须**可验证**：能写成测试用例，或能一步步手动复现。

- [x] 正确账号密码请求返回 200，响应体含 token 字段
- [x] 错误密码返回 401，提示语与「账号不存在」完全一致
- [x] 连续 5 次密码错误后第 6 次返回 423，且 15 分钟内持续返回 423
- [x] token 过期后访问受保护接口返回 401
- [x] 不带 token 访问受保护接口返回 401
- [x] 带合法 token 访问受保护接口返回 200，且只能读到自己的数据
