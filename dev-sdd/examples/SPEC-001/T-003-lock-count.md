# 缺陷卡：T-003 并发下锁定计数丢失

- **关联需求**：`specs/SPEC-001/spec.md`
- **状态**：READY → IN_PROGRESS → DONE

## 一、缺陷描述

- **复现步骤**：
  1. 用脚本并发发起 10 次错误密码登录
  2. 查数据库 `failed_count`
- **期望行为**：计数为 10，第 6 次起返回 423
- **实际行为**：计数为 3～4（随机的），没有触发锁定
- **影响范围**：只影响锁定功能，未写坏业务数据；但暴力破解防护形同虚设

## 二、根因分析

- **根因**：`failed_count = failed_count + 1` 是先 SELECT 读出来、在应用层加一、再 UPDATE 写回。
  并发请求读到同一个旧值，写回时互相覆盖。
- **为什么之前没发现**：手动测试是串行的，串行下这个写法完全正确。

## 三、修复方案

- **改法**：改成数据库原生原子自增 `UPDATE users SET failed_count = failed_count + 1 WHERE id = ?`，
  并在同一事务里判断阈值
- **涉及文件**：`services/auth.py`
- **为什么不选另一种改法**：加应用层互斥锁在多进程部署下无效，且会成为性能瓶颈
