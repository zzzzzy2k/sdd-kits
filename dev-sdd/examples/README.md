# examples/ — 样例档案

这里放的是**跑完全程的样例**，用来对照「一层一层写到什么程度才算到位」。

项目、代码、数字**全部虚构**。

## 目录

| 路径 | 看点 |
|---|---|
| `SPEC-001/spec.md` | 注意「零、状态流转记录」和「六、变更记录」——需求不是一次成型的 |
| `SPEC-001/review.md` | 事前评审两次打回（砍范围、补安全），事后复盘写了 3 个真实的坑 |
| `SPEC-001/T-001~003` | 三张任务卡，kind 不同验收清单就不同；T-003 是缺陷卡，重点是「根因」 |
| `ADR-001.md` | 选项对比里连「不做」都列了；关键是第四节最后那句「什么情况下重新考虑」 |
| `auth-jwt/` | 一次做完的方案沉淀成包，下一笔直接引用 |

## 三个最值得抄的习惯

1. **out-of-scope 写得比 deliverables 还具体** —— 样例里砍掉了第三方登录、短信登录、密码找回三项，
   每一项都写了「为什么不在这做」。需求膨胀就是靠这个挡住的。
2. **ADR 必须写「什么情况下重新考虑」** —— 没有这句，半年后这条决策就变成没人敢动的历史包袱。
3. **缺陷卡必须有「根因」和「为什么之前没发现」** —— 只修症状的 bug 会以别的形式回来。

## 注意

`examples/` 不在 `guard_dev.py` 的校验范围内（它是档案，不是活数据）。
真实使用时：需求在 `specs/<id>/`，任务在 `tasks/<id>/`，ADR 在 `adr/`，方案包在 `modules/<id>/`。

想自己从头跑一遍：

```bash
python bin/init_dev.py spec SPEC-001 你的需求名
```
