# ADR-001：会话状态用 JWT 还是服务端 Session

> 一条 ADR 只记**一个决策**。

## 一、背景

- **要解决的问题**：登录成功后，后续请求怎么识别「你是谁」
- **约束条件**：单体应用、单台服务器、无 Redis；要求两周内交付

## 二、选项对比

| 选项 | 优点 | 缺点 | 可行性 |
|---|---|---|---|
| A. JWT | 无状态，不依赖存储；扩容简单；前端好处理 | 无法主动吊销；token 体积大 | 可行，2 天 |
| B. 服务端 Session | 可主动踢下线；实现最成熟 | 需要存储（内存重启即丢，上 Redis 就多一个组件） | 可行，3 天 + 运维成本 |
| C. 不做认证 | 零成本 | 合同要求多用户隔离，交付不了 | 不可行 |

## 三、决策

> 选定：**A. JWT**

- **理由**：当前是单机部署、无 Redis，Session 的内存存储重启即丢，等于必须引入 Redis。
  JWT 的「无法主动吊销」这个缺点，在当前业务下可以用「token 有效期压到 2 小时」来缓解。
- **放弃其他选项的原因**：B 多引入一个组件，对本阶段的复杂度不划算；C 不可行。

## 四、后果

- **好处**：无状态，服务器重启不影响登录态；不需要额外存储组件
- **代价**：**账号被锁或改密码后，已签发的 token 在有效期内依然有效**。这个代价已明确接受。
- **什么情况下应该重新考虑这条决策**：出现以下任一情况就重新评估 ——
  1. 需要「立即踢下线」的能力（比如出了安全事件）
  2. 需要单点登录 / 多端互斥
  3. 部署从单机变成多实例且要共享登录态（那时 Session + Redis 反而更简单）
