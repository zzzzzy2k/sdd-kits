# RULES.md · 工程规范基准

> **这是本体系的最高约束**。需求规格的 validation 引用它，`guard_dev.py` 从它读数值做校验。
> 规则定义权在你手里 —— AI 只负责执行与兜底，不替你改规则。
>
> 改规则 = 改下面 `RULES-BEGIN / RULES-END` 之间的键值对。**格式别动**，脚本靠它解析。

max_task_hours = 8

| 键 | 含义 | 默认值 | 怎么改 |
|---|---|---|---|
| `max_task_hours` | 单任务工时上限（超过必须拆） | 8 | 超过半天的任务就该拆，别硬扛 |
| `min_acceptance_items` | 需求至少几条验收标准 | 3 | 少于 3 条说明需求没想清楚 |
| `max_acceptance_items` | 单项任务最多几条验收项 | 8 | 超过 8 条说明这个任务该拆 |
| `require_tests` | 功能/缺陷任务是否必须有测试 | true | 前期放过可设 false，但别长期关 |
| `require_adr_accepted` | 引用的 ADR 是否必须 accepted | true | 同上 |
| `forbid` | 禁止项清单 | 见上 | 加你自己的雷区 |

## 一、通用纪律（硬约束）

- **没有 accepted 的需求，不写业务代码** —— 这是地基
- **不硬编码密钥**（口令 / Token / 数据库连接串），一律走配置或环境变量
- **不直接改生产库**，任何变更走脚本 + 可回滚
- **不留注释掉的死代码**，删掉就是删掉了，靠版本控制找回
- **破坏性变更必须先评审**（删字段、改协议、改数据结构）

## 二、需求规定

- 每个需求必须有 **背景与问题**、**不做什么**、**可验证的验收标准**
- **不做什么**必须写，且要比"要做什么"具体 —— 需求膨胀都发生在"顺手多做一点"
- 需求一旦 accepted，**改范围必须写变更记录**，并重新过评审
- 验收标准不许写「功能正常」「没问题」这类空话，要能写成测试用例

## 三、任务规定

- **单任务预估工时 > 8 小时必须拆** —— 拆不了说明方案还没想清楚
- 任务卡必须关联一个 accepted 的需求，不许有孤儿任务
- 开工前状态改 IN_PROGRESS，卡住改 BLOCKED **并写原因**，不许无声挂着
- 验收清单全勾才能 DONE —— 少勾一项就是留着下个人踩

## 四、质量规定

- 功能任务：**先写测试还是后写测试都行，但必须有测试**
- 缺陷修复：**必须把复现步骤固化成测试用例**，否则这个 bug 会以别的形式回来
- 重构：**不改外部行为**，测试全绿是唯一验收标准
- 提交粒度：一个任务可以多次提交，但一次提交只做一件事

## 五、复盘规定

- 每个需求 done 前必须复盘：**目标达成对照 + 返工次数 + 踩到的坑**
- 复盘中可复用的做法 → 沉淀成 `modules/` 方案包
- 复盘中不可逆的技术选型 → 沉淀成 `adr/` 决策记录
- **规则漏洞 → 追加到本文件**（这是经验沉淀的唯一入口）
